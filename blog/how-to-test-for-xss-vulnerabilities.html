How to Test for XSS Vulnerabilities (And Why Most Scanners Miss Them)

Cross-site scripting remains one of the most prevalent web vulnerabilities, yet most automated scanners fail to detect it in modern applications. Here is how to test properly.

You run a vulnerability scan against your web application. The report comes back clean. Two weeks later, a bug bounty researcher demonstrates account takeover through an XSS vulnerability that exists on your profile settings page. The scanner missed it because the payload only executes after three JavaScript event handlers fire in sequence. This scenario repeats constantly across the industry.

Testing for XSS vulnerabilities requires understanding the three distinct types, recognizing where automated tools fail, and applying manual verification techniques that match how modern applications actually render content.

The Three Types of XSS You Must Test For

Each XSS variant has different attack vectors, different testing methodologies, and different risk profiles. Treating them as interchangeable leads to incomplete assessments.

Reflected XSS

The malicious script arrives via URL parameter or form submission and gets reflected back in the HTTP response without proper encoding. Testing requires identifying every reflection point, determining the output context (HTML body, attribute value, JavaScript string), and crafting payloads specific to that context. A reflection inside a quoted attribute requires breaking out of the quotes before injecting script tags. A reflection inside existing JavaScript requires closing the current statement first.

Stored XSS

The payload persists on the server and executes whenever any user views the affected content. Comment fields, usernames, product descriptions, support tickets, and file metadata are common storage points. Testing requires submitting payloads through every input field and then viewing those inputs through every possible rendering path. A username might be safe when displayed on a profile page but vulnerable when rendered in an admin dashboard with different encoding rules.

DOM-Based XSS

The vulnerability exists entirely in client-side JavaScript. The server never sees the malicious input. Instead, JavaScript reads from sources like document.location, document.referrer, or window.name and writes to dangerous sinks like innerHTML, document.write, or eval(). Automated scanners that only analyze server responses cannot detect this category. Testing requires reading the JavaScript source, tracing data flow from sources to sinks, and constructing URLs that trigger unsafe execution paths.

Why Automated Scanners Fail on Modern Applications

Most XSS scanners operate by sending payloads and checking if they appear unencoded in the response. This approach worked for server-rendered PHP applications in 2010. It fails for modern architectures for several reasons.

The rendering gap: Single-page applications render content through JavaScript frameworks. The initial HTML response contains minimal markup. Content appears after API calls complete and components mount. A scanner analyzing the raw HTTP response sees an empty shell. The XSS vulnerability exists in how the JavaScript processes API data, not in what the server initially returns.

Additional failure modes include:

  • Event-driven execution where payloads only trigger after specific user interactions like clicks, scrolls, or form submissions
  • Multi-step flows where the vulnerable page only loads after completing prior steps in a wizard or checkout process
  • API-driven content where JSON responses get parsed and inserted into the DOM through template engines with inconsistent sanitization
  • Third-party widgets and embedded content that introduce separate rendering contexts with their own security boundaries
  • Conditional logic where vulnerabilities only manifest for specific user roles, feature flags, or A/B test variants

WAF Bypass Techniques That Matter in Testing

Web Application Filters block common XSS patterns. Effective testing requires knowing which bypasses work against real defenses, not just theoretical ones.

Case variation and encoding tricks rarely work anymore. Modern WAFs normalize input before inspection. What does work includes:

  • Context-aware mutations where the payload uses valid syntax for the specific injection point rather than generic script tags
  • Event handler chaining using less-monitored events like onfocus, onmouseover, or ontoggle instead of onload and onerror
  • JavaScript protocol handlers in attributes that accept URLs, combined with whitespace characters that WAFs strip inconsistently
  • Template literal injection in applications using backtick strings, where WAFs expect traditional quote delimiters
  • SVG and MathML namespaces that allow script execution through element names WAFs do not recognize as dangerous

When testing, document which bypasses succeed against each target. This information determines whether your WAF provides meaningful protection or merely creates false confidence.

Detecting Blind XSS

Blind XSS occurs when the payload executes in a context you cannot directly observe. An admin panel renders user-submitted data differently than the public site. A log viewer displays request parameters without encoding. A PDF generator processes HTML input server-side.

Testing for blind XSS requires out-of-band confirmation methods:

  • Callback servers that receive HTTP requests when payloads execute, confirming execution timing and source IP
  • DNS exfiltration where payloads resolve unique subdomains, proving execution even when HTTP callbacks are blocked
  • Time-based delays using synchronous operations that cause measurable response latency differences
  • Data exfiltration to external endpoints that confirm both execution and access to sensitive values like cookies or tokens

Submit blind XSS payloads through every input vector: contact forms, support tickets, file uploads, feedback widgets, error reports, and API endpoints. Then monitor your callback infrastructure for hours or days. Many blind XSS vulnerabilities trigger during asynchronous processing cycles unrelated to your submission timing.

A Practical Testing Methodology

Structure your XSS testing in phases that build coverage systematically.

First, map all input vectors. Enumerate URL parameters, form fields, headers, API endpoints, and file upload handlers. Document where each input appears in responses and through which rendering paths.

Second, classify output contexts. For each reflection or storage point, determine whether the output lands in HTML body content, attribute values, JavaScript strings, CSS contexts, or URL schemes. Each context requires different payload structures and different encoding bypasses.

Third, test with context-appropriate payloads. Use polyglot strings that validate multiple contexts simultaneously. Progress to targeted payloads once you understand the specific escaping mechanisms in use.

Fourth, verify execution in actual browsers. Confirm that payloads execute in Chrome, Firefox, and Safari. Some browser-specific parsing quirks create vulnerabilities that exist in one engine but not others.

Fifth, assess impact. Determine what the executed JavaScript can access: session tokens, CSRF protections, sensitive DOM content, or privileged API endpoints. Not all XSS carries equal risk.

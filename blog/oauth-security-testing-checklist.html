OAuth Security Testing Checklist: What to Verify Before Going Live

OAuth implementations fail in predictable ways. This checklist covers the five verification points that separate secure auth flows from account takeover vulnerabilities.

OAuth 2.0 is the de facto standard for delegated authorization, but its flexibility creates attack surface. The specification provides security mechanisms; whether your implementation actually uses them correctly is a different question entirely. Most OAuth breaches we investigate stem from misconfiguration rather than protocol flaws.

This oauth security testing checklist focuses on verifiable technical controls. Each item can be tested programmatically or through manual inspection of authorization requests and token responses.

1. Redirect URI Validation

The redirect URI is where the authorization server sends the user after consent. If an attacker can control this parameter, they can intercept authorization codes or tokens directly.

Exact Match Enforcement

Your authorization server must compare the redirect_uri parameter against a pre-registered allowlist using exact string matching. Substring matching, prefix matching, and regex patterns all introduce bypass opportunities.

No Wildcards or Open Redirects

Reject any registration containing wildcards (*) or path traversal sequences. Verify that none of your registered redirect targets are themselves open redirect endpoints elsewhere in your application.

Scheme Validation

For web applications, only permit https:// schemes. Custom URI schemes for mobile apps should use reverse-domain notation (e.g., com.example.app://callback) and be validated against the registered value exactly.

Testing method: Attempt authorization requests with modified redirect URIs: different subdomains, added path segments, query parameter injection, and fragment manipulation. All variations must be rejected with an error response, never a silent redirect.

2. State Token Requirements

The state parameter binds the authorization request to the user's session and prevents cross-site request forgery attacks against the callback endpoint.

Cryptographic Randomness

State values must be generated using a cryptographically secure random number generator. Predictable state values (timestamps, sequential IDs, UUIDs without entropy) defeat the purpose entirely.

Server-Side Binding and Validation

Store the state value server-side associated with the user's session before redirecting to the authorization server. On callback, validate that the returned state matches the stored value exactly, then invalidate it immediately after use.

Rejection on Missing or Invalid State

If the callback arrives without a state parameter, or with a state that does not match, the authorization flow must terminate. Do not proceed with token exchange.

State also enables encoding of post-login destination URLs securely. If you embed return paths in state, sign or encrypt the value to prevent tampering.

3. PKCE Detection and Enforcement

Proof Key for Code Exchange (PKCE, RFC 7636) mitigates authorization code interception attacks, particularly for public clients that cannot securely store client secrets.

Code Verifier Entropy

Verify that the code_verifier is between 43 and 128 characters and uses only unreserved URL-safe characters. The corresponding code_challenge should be the base64url-encoded SHA-256 hash of the verifier.

Mandatory for Public Clients

If your application is a single-page app, mobile app, or desktop client without a backend component capable of holding secrets, PKCE is not optional. Your authorization server should reject token requests from public clients that lack valid PKCE parameters.

Challenge Method Validation

Confirm the code_challenge_method is S256. The plain method provides no security benefit and should be disabled at the server level.

Even confidential clients benefit from PKCE as defense-in-depth against code leakage through logs, referrer headers, or browser history.

4. Scope Permission Analysis

Scopes define what the access token can do. Overly broad scopes expand the blast radius of token compromise.

Principle of Least Privilege

Audit every scope requested during authorization. Each scope should map to a specific, documented capability. Remove any scope that is not actively consumed by your application logic.

User Consent Transparency

The consent screen must clearly describe what each granted scope permits. Vague descriptions like "access your account" obscure the actual permissions being delegated.

Scope Downgrading on Refresh

When refreshing tokens, verify that the new access token cannot escalate beyond the original granted scopes. Some implementations incorrectly allow scope expansion during refresh without re-consent.

5. Common OAuth Misconfigurations

Beyond the core mechanisms above, these recurring issues appear across production deployments:

  • Token leakage via referrer headers: Access tokens passed in URL fragments or query strings may leak to third parties through the HTTP Referer header. Always transmit tokens in Authorization headers or POST bodies.
  • Insufficient token lifetime management: Access tokens with multi-day lifetimes increase exposure windows. Pair short-lived access tokens (15 minutes or less) with refresh tokens that support rotation and revocation.
  • Missing audience validation: Resource servers must verify the token's aud claim matches their own identifier. Accepting tokens intended for other services enables lateral movement.
  • Implicit grant usage: The implicit flow returns tokens directly in the URL fragment and is deprecated in OAuth 2.1. Migrate to authorization code flow with PKCE.
  • Client secret exposure: Embedding client secrets in frontend code, mobile binaries, or public repositories converts confidential clients into public ones. Secrets belong exclusively on backend servers.

Verification Cadence

Run this checklist at three points: during initial implementation review, before each production deployment that touches authentication code, and quarterly as part of broader application security assessment. OAuth configurations drift as teams add new integrations, update libraries, or modify infrastructure.

Document test results alongside your authorization architecture decisions. When an incident occurs, having verified baseline behavior accelerates root cause analysis significantly.

How to Scan GitHub Repo for Secrets: Find Leaked Keys, .env Files & RLS Gaps

Public GitHub repositories are a goldmine for attackers. Hardcoded API keys, committed .env files, and missing Row Level Security policies expose backend services the moment code goes live. This guide shows you exactly what to look for and how to catch these issues before they become breaches.

Why Secret Scanning Matters Before Merge

GitHub's own secret scanning catches many patterns after push, but it only covers known formats and only triggers on public repos by default. Attackers use automated crawlers that index every public commit within minutes. If your AWS key, Stripe secret, or Supabase service role appears in any reachable ref, bots will find it long before your team notices.

The problem extends beyond obvious string literals. Developers frequently commit .env files during initial setup, forget to add them to .gitignore, and leave production credentials in history even after deletion. Git retains every blob indefinitely. A single overlooked file can invalidate months of security work.

Finding Hardcoded API Keys and Tokens

Start with pattern matching against known credential formats. Most cloud providers publish regex patterns for their keys:

  • AWS Access Keys: Match AKIA[0-9A-Z]{16} in all source files and config directories.
  • Stripe Secrets: Look for sk_live_[0-9a-zA-Z]{24,} and test variants.
  • GitHub PATs: Search for ghp_[0-9a-zA-Z]{36} and fine-grained token prefixes.
  • Supabase Service Roles: Target JWT strings beginning with eyJ paired with anon key references.

Run these searches across branches, tags, and stashes. Check pull request diffs separately since unmerged code still lives in refs accessible to anyone with read access. Automated tools handle this breadth better than manual grep sessions.

Detecting Exposed .env Files and Config Leaks

Environment files deserve special attention because they concentrate multiple secrets in one place. Search for filenames matching .env*, *.env.local, .env.production, and similar variants. Also check for:

  • Config files (config.json, settings.yaml) containing connection strings or passwords.
  • Terraform state files (*.tfstate) with embedded provider credentials.
  • Kubernetes manifests with base64-encoded secrets that decode to plaintext.
  • Docker Compose files passing environment variables directly instead of referencing external secrets.

Verify that .gitignore actually excludes these patterns. Many projects list .env but miss .env.* or platform-specific variants. Run git ls-files --cached to see what Git currently tracks regardless of ignore rules.

Checking Supabase Row Level Security Gaps

Supabase projects introduce a distinct risk category: missing or permissive Row Level Security policies. When RLS is disabled on a table, any authenticated user (or anonymous client if auth is bypassed) can read and write all rows. This misconfiguration causes more data leaks than stolen credentials in modern stacks.

Scan migration files and schema definitions for tables lacking ALTER TABLE ... ENABLE ROW LEVEL SECURITY. Review policy definitions for overly broad conditions like USING (true) or policies that reference no auth.uid() checks. Verify that service role keys never appear in frontend code, since those keys bypass RLS entirely.

Cross-reference exposed tables with public endpoints. A table without RLS behind an authenticated route may be acceptable; the same table exposed via PostgREST without middleware is an open database.

Scanning Commit History, Not Just HEAD

Credentials removed from current files still exist in historical commits. Use git log -p --all or dedicated history scanners to search every blob ever pushed. Pay attention to:

  • Force-pushes that rewrote history but left orphaned refs.
  • Merge commits that reintroduced deleted secrets from feature branches.
  • Tagged releases pointing to commits containing temporary debug credentials.

If you discover secrets in history, assume compromise. Rotate immediately. Do not rely solely on git filter-repo or BFG Repo-Cleaner to "fix" the issue; GitHub caches objects aggressively, and forks retain copies outside your control.

Automating Continuous Secret Detection

Manual scans establish a baseline, but prevention requires automation. Integrate secret scanning into pre-commit hooks, CI pipelines, and PR review gates. Configure alerts for new matches so remediation happens before merge rather than after incident response.

Track false positives explicitly. Maintain an allowlist of benign patterns (documentation examples, test fixtures with dummy values) to reduce alert fatigue. Review allowlisted entries quarterly since legitimate patterns change as dependencies update.

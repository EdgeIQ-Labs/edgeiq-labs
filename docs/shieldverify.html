ShieldVerify Documentation

Overview

ShieldVerify is a third-party security verification service that independently validates the security posture of your infrastructure, applications, and vendor integrations. Unlike automated scanners, ShieldVerify combines automated testing with manual review to produce a signed verification report suitable for compliance audits, vendor assessments, and customer trust demonstrations.

Verification engagements are scoped per target (domain, application, or vendor integration) and produce a deterministic pass/fail outcome with detailed evidence. Reports are cryptographically signed and timestamped for audit integrity.

Initiating Verification

To start a ShieldVerify engagement:

  1. Navigate to Dashboard → ShieldVerify → New Request.
  2. Select the verification scope: Web Application, Infrastructure, Vendor Integration, or Custom.
  3. Provide target identifiers (domains, IPs, API endpoints, or vendor names).
  4. Upload any required authorization documents (e.g., pentest authorization letters for infrastructure scopes).
  5. Choose verification depth: Standard (automated + spot-check) or Deep (full manual validation).
  6. Confirm pricing tier and submit the request.

You will receive a confirmation email with an estimated completion window. Standard verifications typically complete within 48 hours; Deep verifications take 5–7 business days.

Checks Performed

The exact checks depend on scope type. Below is the baseline coverage matrix:

  • TLS/SSL: Certificate validity, chain trust, cipher suite strength, HSTS enforcement, OCSP stapling.
  • HTTP Security Headers: CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy.
  • Authentication & Session: Password policy enforcement, MFA availability, session token entropy, cookie flags.
  • Vulnerability Scan: OWASP Top 10 automated sweep with false-positive triage.
  • DNS & Email Security: SPF, DKIM, DMARC alignment; CAA records; DNSSEC validation.
  • Vendor Integration (if applicable): API key rotation evidence, webhook signature verification, least-privilege scope audit.
  • Data Exposure: Public bucket/object storage enumeration, source map leakage, debug endpoint detection.

Deep-tier engagements add manual penetration testing, business logic review, and configuration audit against CIS benchmarks.

Reading Results

Each verification produces a structured report with three sections:

  1. Executive Summary: Pass/Fail verdict, risk score (0–100), and top 3 findings.
  2. Detailed Findings: Each check listed with status (PASS, FAIL, WARN, INFO), evidence (screenshots, raw responses, timestamps), and severity classification.
  3. Attestation Block: Cryptographic signature, verifier identity, timestamp, and report hash for tamper-evidence.

Status definitions:

  • PASS — Control verified and meets baseline requirements.
  • FAIL — Control missing or misconfigured; blocks verification.
  • WARN — Suboptimal configuration; does not block but reduces risk score.
  • INFO — Observational note; no security impact.

A single FAIL results in an overall Fail verdict. All failures must be remediated and re-verified to achieve a passing status.

Remediation Guidance

Every FAIL and WARN finding includes a remediation block with:

  • Description: What is wrong and why it matters.
  • Fix Instructions: Step-by-step correction specific to your platform (e.g., Nginx config snippet, AWS console path, Cloudflare rule).
  • Validation Command: A command or test you can run locally to confirm the fix before requesting re-verification.
  • Reference: Link to relevant standard (OWASP, CIS, RFC) or vendor documentation.

If you use the EdgeIQ Fix-It Engine, compatible findings can be auto-remediated directly from the report. Enable this via Dashboard → ShieldVerify → Auto-Remediate.

Re-Verification Workflow

After remediating findings:

  1. Open the original report in the dashboard.
  2. Click Request Re-Verification. This is free within 30 days of the original report.
  3. Only previously failed/warned checks are re-executed unless you explicitly request a full rescan.
  4. Updated results are appended to the original report with a new attestation block; prior findings are preserved for audit trail.

Re-verification turnaround is typically 24 hours for Standard tier and 48 hours for Deep tier. After 30 days, a new verification request at the applicable tier price is required.

API Access

ShieldVerify exposes a REST API for programmatic access. Authentication uses Bearer tokens generated at Dashboard → Settings → API Keys.

# Initiate verification
POST /api/v1/shieldverify/requests
Authorization: Bearer sk_live_xxxxx
Content-Type: application/json

{
  "scope_type": "web_application",
  "target": "app.example.com",
  "depth": "standard"
}

# Check status
GET /api/v1/shieldverify/requests/{request_id}

# Download report (PDF)
GET /api/v1/shieldverify/reports/{report_id}/pdf

# List all verifications
GET /api/v1/shieldverify/requests?status=completed&limit=20

Rate limits: 60 requests/minute per API key. Webhook notifications for completion events can be configured at Dashboard → Integrations → Webhooks.

Troubleshooting

  • Verification stuck in "Pending Authorization": Ensure uploaded authorization documents are valid PDFs under 5 MB and contain matching target identifiers. Re-upload if needed.
  • Report shows unexpected FAIL: Check the evidence block for timestamp and request headers. If the target was undergoing maintenance during the scan window, file a dispute via Report → Dispute Finding with supporting logs.
  • API returns 403: Verify the API key has ShieldVerify scope enabled. Regenerate keys at Settings → API Keys if compromised.
  • Re-verification not picking up fixes: Confirm changes are deployed to the exact target specified in the original request. CDN caches may serve stale configurations; purge cache before re-verification.
  • Webhook not firing: Test endpoint reachability via Integrations → Webhooks → Test. Ensure response code is 2xx within 10 seconds; timeouts are treated as delivery failures.

Overview

Cert Alert is the certificate-monitoring variant of EdgeIQ Labs Workspace Posture Pro. It continuously checks SSL/TLS certificates across your domains for upcoming expiry and common misconfigurations, sending timely alerts so you never face an unexpected outage due to a lapsed cert. Designed for DevOps teams, sysadmins, and anyone managing multiple domains who needs reliable, hands-off certificate visibility.

  • Monitor SSL/TLS certificate expiry across unlimited domains
  • Automated alerts at 30, 14, 7, and 1 day(s) before expiry
  • Detect misconfigurations: weak ciphers, incomplete chains, mismatched hostnames, expired intermediates
  • Support for public CAs, private CAs, and custom certificate sources
  • REST API for integration into CI/CD pipelines and SOAR workflows

Setup

Adding Domains

Add domains individually or in bulk via the CLI or dashboard. Cert Alert resolves each domain, connects over TLS, and extracts the presented certificate chain automatically.

# Add a single domain
cert-alert add example.com

# Add multiple domains from a file
cert-alert add --file domains.txt

# Add with explicit port (non-standard HTTPS)
cert-alert add mail.example.com:465

# List all monitored domains
cert-alert list

Certificate Sources

Cert Alert supports multiple certificate sources beyond live TLS handshakes:

SourceFlag / ConfigDescription
Live TLS--source tlsDefault. Connects to the domain and reads the served certificate chain.
Local PEM file--source file --path /etc/ssl/cert.pemMonitor a certificate file on disk directly.
Kubernetes Secret--source k8s-secret --namespace default --secret tls-certPull and monitor certs stored as K8s TLS secrets.
AWS ACM--source acm --region us-east-1Monitor certificates managed in AWS Certificate Manager.
Custom CA Bundle--ca-bundle /path/to/ca.pemValidate against a private or custom CA bundle.
When using non-TLS sources, Cert Alert still applies all misconfiguration checks against the provided certificate data.

Alert Configuration

Cert Alert ships with sensible defaults: notifications fire at 30, 14, 7, and 1 day(s) before a certificate expires. You can customize thresholds and delivery channels per domain or globally.

# Set custom alert thresholds (days before expiry)
cert-alert config set --thresholds 60,30,14,7,1

# Configure webhook alerts (Slack, Discord, generic)
cert-alert config set --alert-webhook https://hooks.slack.com/services/xxx

# Configure email alerts
cert-alert config set --alert-email ops@example.com

# Test alert delivery
cert-alert alert test

# View current alert configuration
cert-alert config show

Alert Payload

Webhook payloads are JSON and include the domain, expiry date, days remaining, issuer, and any detected misconfigurations:

{
  "event": "cert_expiry_warning",
  "domain": "example.com",
  "expires_at": "2026-12-07T00:00:00Z",
  "days_remaining": 30,
  "issuer": "Let's Encrypt Authority X3",
  "misconfigurations": [],
  "severity": "warning"
}

Misconfiguration Detection

Beyond expiry, Cert Alert inspects every monitored certificate for common TLS misconfigurations that degrade security or cause client trust failures.

CheckSeverityDescription
Incomplete chainCriticalIntermediate certificates missing; clients may fail to build a trust path.
Hostname mismatchCriticalCertificate CN/SAN does not match the monitored domain.
Expired intermediateCriticalAn intermediate CA in the chain has expired even if the leaf is valid.
Weak signature algorithmHighSHA-1 or other deprecated signature algorithms detected.
Short key lengthHighRSA keys under 2048 bits or ECDSA keys under 256 bits.
Self-signedHighCertificate is self-signed and not trusted by public roots.
TLS 1.0/1.1 supportMediumServer negotiates deprecated TLS versions alongside the cert.
No OCSP staplingLowOCSP stapling not enabled; revocation checks rely on client fetching.
# Run a one-time misconfiguration audit
cert-alert audit example.com

# Audit all monitored domains
cert-alert audit --all

# Export audit results as JSON
cert-alert audit --all --format json > audit-report.json
Misconfiguration checks run alongside every scheduled monitoring cycle. Alerts include both expiry warnings and new misconfiguration findings.

API Reference

All CLI functionality is available via REST API when running cert-alert serve --port 8401.

Endpoints

MethodPathDescription
GET/api/v1/certsList all monitored certificates and their status
POST/api/v1/certsAdd a new domain or certificate source to monitor
GET/api/v1/certs/{id}Retrieve details for a specific certificate
DELETE/api/v1/certs/{id}Remove a certificate from monitoring
POST/api/v1/certs/{id}/auditTrigger an on-demand misconfiguration audit
GET/api/v1/alertsList recent alert history
PUT/api/v1/configUpdate alert thresholds and delivery channels

Example: Add a Domain via API

curl -X POST http://localhost:8401/api/v1/certs \
  -H "Content-Type: application/json" \
  -d '{
    "domain": "example.com",
    "source": "tls",
    "port": 443,
    "alert_thresholds": [30, 14, 7, 1]
  }'

Example: Retrieve Certificate Status

curl http://localhost:8401/api/v1/certs/abc123

Troubleshooting

Common Issues

Certificate shows as expired but site works fine: The server may be serving a different certificate than expected (e.g., SNI mismatch). Use cert-alert audit example.com --verbose to inspect the full chain and verify SNI behavior.

Connection refused or timeout during check: Ensure the target port is open and reachable from the Cert Alert host. If behind a firewall, whitelist the monitoring IP or use a local agent deployment.

Alerts not firing at expected thresholds: Verify your configuration with cert-alert config show. Check ~/.edgeiq/logs/cert-alert.log for delivery errors. Test manually with cert-alert alert test.

False positive on incomplete chain: Some servers intentionally omit cross-signed roots. If the chain validates correctly in browsers, suppress the finding with cert-alert config set --ignore-check incomplete-chain --domain example.com.

Private CA certificates flagged as untrusted: Provide your internal CA bundle with --ca-bundle /path/to/internal-ca.pem so Cert Alert can validate against your private root.

Kubernetes secret access denied: Ensure the service account running Cert Alert has get permissions on secrets in the target namespace.

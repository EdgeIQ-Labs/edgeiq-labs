Finding #1: Email Authentication Is Broken for Most SMBs

SPF, DKIM, and DMARC exist for one reason: preventing attackers from sending email that looks like it came from your domain. Without them, anyone can impersonate your CEO, your billing department, or your support team. Our SPF checker data reveals how widespread the gap is.

⚠️ 73% of domains have SPF misconfigurations

The most common issue: using ~all (soft fail) instead of -all (hard fail). Soft fail tells receiving servers to accept suspicious email but mark it. Hard fail tells them to reject it outright. Attackers know which domains use soft fail — they specifically target them for phishing campaigns because the email will still land in inboxes.

🔴 31% exceed the 10 DNS lookup limit

RFC 7208 caps SPF evaluation at 10 DNS lookups. Every include:, mx, and a mechanism counts. When teams add new email services (marketing platforms, CRM tools, ticketing systems) without checking their SPF record, they silently push past this limit. Once exceeded, SPF returns PermError — meaning every sender fails, including legitimate ones. Check your domain with our free SPF checker to see where you stand.

⚠️ 58% have no DMARC policy or use p=none

SPF alone doesn't protect the visible From address. DMARC enforces alignment between SPF/DKIM and what the recipient sees. A p=none policy means "monitor but don't block" — effectively leaving the door open. Our DMARC checker shows exactly what policy your domain enforces.

The pattern is clear: teams set up email authentication once during initial configuration, then never revisit it as their stack grows. Each new SaaS tool added to the email flow creates potential breakage that goes undetected until deliverability drops or a spoofing incident occurs.

Finding #2: SSL Certificates Are Ticking Time Bombs

SSL certificate expiry sounds like a solved problem. Let's Encrypt auto-renews, right? Except when it doesn't. Our SSL checker scans reveal that certificate management remains a significant blind spot.

Auto-renewal fails silently. DNS challenges break when records change. Webroot paths shift during deployments. The certificate expires, the site throws browser warnings, customers bounce, and the team finds out from a support ticket — not from monitoring.

Beyond expiry, header misconfigurations create attack surface that scanners catch but teams miss. Missing HSTS allows downgrade attacks. Exposed server headers give attackers reconnaissance data for free. These aren't exotic vulnerabilities — they're configuration hygiene.

Finding #3: Open Source Repositories Leak Secrets Constantly

Our repository scanner analyzes GitHub projects for exposed secrets, weak dependency configurations, and CI pipeline risks. The findings follow a predictable pattern across organizations of every size.

🔴 API keys in commit history

The most critical finding across scanned repositories: hardcoded credentials buried in git history. Even after removing the key from the current codebase, it persists in previous commits. Attackers use automated tools to scrape public repos for exactly this pattern. Rotating the key is the only fix — deleting the commit doesn't help once it's been cloned.

⚠️ Outdated dependencies with known CVEs

Teams pin dependency versions and forget them. Six months later, those packages have published CVEs that go unpatched because no one is watching. Our scanner flags these automatically, but the remediation requires someone to actually act on the findings.

⚠️ Permissive CI/CD configurations

GitHub Actions workflows running with excessive permissions, pull request triggers executing arbitrary code from forks, deployment secrets accessible to test jobs. These misconfigurations turn CI pipelines into attack vectors.

The Common Thread: Manual Checks Don't Scale

A certificate renewal fails quietly. An intern commits a test API key. The problems return because nothing watches for them continuously.

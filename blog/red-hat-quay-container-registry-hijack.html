Red Hat Quay CVE-2026-123710: How Attackers Can Hijack Your Container Registry

Container Security Supply Chain Critical CVE

A CVSS 9.8 vulnerability in Red Hat Quay lets any authenticated user steal image signing keys, overwrite private repositories, and lock out legitimate operators. Disabling anonymous access doesn't protect you. Fixes merged November 11.

Container registries are trust anchors. When your CI/CD pipeline pulls an image from Quay, it assumes that image is what you built and signed. CVE-2026-123710 breaks that assumption completely.

Red Hat disclosed the vulnerability on November 12. Fixes were merged to the project's GitHub repository on November 11, but no specific patched release version has been identified in the advisory or Bugzilla report as of this writing. If you run Red Hat Quay in any capacity, check your version against upstream commits and plan accordingly.

What the vulnerability does

The flaw exists in Quay's signing key management service. When this service is accessible to untrusted clients, an attacker with any valid Quay account can exploit it to:

  • Steal private signing keys used to verify container image integrity
  • Overwrite private container images in repositories they shouldn't have access to
  • Delete legitimate instance keys as a side effect of key rotation, breaking normal registry operations
  • Maintain persistent access by injecting their own signing keys that survive routine key rotation

The critical detail: turning off anonymous access doesn't help. Any authenticated user, including low-privilege accounts, can exploit this flaw. If someone has a login to your Quay instance, they can potentially take over the entire registry.

Why container registry compromise matters

This isn't just about stolen source code or leaked proprietary applications. A compromised registry enables supply chain attacks at scale.

When an attacker can overwrite images and control signing keys, they can inject malicious code into containers that your production systems pull automatically. Your deployment pipeline trusts the registry. Your orchestration platform trusts the signatures. The malicious image passes validation, gets deployed, and runs with whatever permissions your application has.

We've seen this pattern before. In 2024, attackers compromised npm packages to inject cryptocurrency miners. In 2025, PyPI faced repeated supply chain attacks through typosquatting and maintainer account takeovers. Container registries represent the same attack surface with higher stakes, because compromised containers often run with elevated privileges in production environments.

The persistence mechanism is particularly concerning. By injecting their own signing keys, attackers ensure that even if you rotate credentials and rebuild images, their malicious keys remain valid. Routine key rotation deletes legitimate keys as a side effect, which can cause operational disruption while the attacker maintains access. This creates a scenario where fixing the symptoms actually helps the attacker stay hidden.

Who's affected

The vulnerability affects Red Hat Quay deployments where the signing key management service is accessible to untrusted clients. This includes:

  • Self-hosted Quay instances with default or permissive configurations
  • Deployments where internal users have accounts but shouldn't have signing key access
  • Multi-tenant Quay installations where tenant isolation relies on application-level controls rather than network segmentation

Red Hat released container images for Quay versions 3.17.7 and 3.12.24 on November 11 under security advisories RHSA-2026:99026 and RHSA-2026:99027. These advisories address both CVE-2026-123710 and a related flaw tracked as CVE-2026-110697. However, neither the advisories nor the Bugzilla reports explicitly state which versions contain the fix for CVE-2026-123710 specifically.

What to do right now

Check your Quay version. If you're running 3.17.x or 3.12.x, update to 3.17.7 or 3.12.24 respectively. If you're on an older major version, plan an upgrade path immediately.

Audit signing keys. List all signing keys in your Quay instance. Compare against your expected inventory. Look for keys you don't recognize or keys created outside your normal provisioning workflow. Revoke anything suspicious.

Review image integrity. For critical images pulled since the potential exposure window, verify checksums against known-good builds. If you can't verify provenance, rebuild from source and re-sign with fresh keys.

Rotate all signing keys. After confirming the patch is applied, generate new signing keys and revoke all existing ones. Update your CI/CD pipelines and deployment configurations to use the new keys. Yes, this will cause temporary disruption. The alternative is operating with potentially compromised keys.

Restrict signing key service access. Network-segment the signing key management service so only trusted build infrastructure can reach it. Application-level access controls aren't sufficient when the application itself is vulnerable.

Audit user accounts. Review all Quay user accounts. Remove inactive accounts. Ensure principle of least privilege. Consider whether every account actually needs registry access or whether some workflows can use read-only tokens with restricted scope.

Broader lessons for container security

This vulnerability highlights a recurring theme in container infrastructure: signing and verification are only as strong as the systems that manage the keys.

Many organizations implement container signing as a checkbox exercise. They enable cosign or Notary, configure policy enforcement, and consider the problem solved. But if the key management backend has a vulnerability like CVE-2026-123710, all that signing infrastructure becomes theater. The attacker controls the trust anchor.

A few practices worth adopting:

Separate key management from registry operations. Don't let the same service that stores images also manage the keys that verify them. Use dedicated key management infrastructure with strict access controls and independent monitoring.

Monitor key operations independently. Log signing key creation, rotation, and deletion to a system outside the registry. Alert on anomalous key activity. If someone creates a signing key at 3 AM on a Saturday, you want to know about it before the next deployment cycle.

Verify images at runtime, not just at deploy time. Admission controllers catch bad images before they start, but runtime verification catches images that were good at deploy time and compromised afterward. Tools like Sigstore's Rekor provide transparency logs that enable continuous verification.

Treat registry infrastructure like production systems. Patch promptly. Monitor actively. Segment aggressively. Your registry isn't a development tool; it's part of your production supply chain. Give it the same operational rigor you'd give a database or payment processor.

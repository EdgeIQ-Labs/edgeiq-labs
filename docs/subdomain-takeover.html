Overview

Subdomain Takeover Scanner continuously monitors your DNS infrastructure for dangling CNAME, A, AAAA, NS, and MX records that point to deleted or unclaimed cloud resources. When a service like an S3 bucket, Heroku app, GitHub Pages site, or Azure endpoint is removed but its DNS record remains, attackers can register the same resource name and hijack the subdomain to serve malicious content, steal credentials, or bypass email security controls.

  • Detects takeovers across 40+ cloud providers (AWS, GCP, Azure, Heroku, Shopify, GitHub, etc.)
  • Supports CNAME, A, AAAA, NS, and MX record types
  • Automatic risk scoring based on record type, provider, and exploitability
  • Step-by-step remediation guidance per finding
  • REST API for integration into vulnerability management and SOAR workflows

Setup

Adding Root Domains

Add each root domain you want to monitor. The scanner enumerates all subdomains via certificate transparency logs, DNS brute-force, and passive reconnaissance before checking each one for takeover conditions.

# Add a root domain via CLI
subtakeover domain add example.com

# Add multiple domains from a file
subtakeover domain add --file domains.txt

# List monitored domains
subtakeover domain list

Detection Logic

The scanner evaluates each DNS record against a fingerprint database of known vulnerable cloud service endpoints. Detection follows a three-stage pipeline:

  1. Enumeration: Discover all subdomains via CT logs, DNS zone transfers (when permitted), wordlist brute-force, and passive data sources.
  2. Resolution: Resolve each subdomain and classify the record type (CNAME, A, AAAA, NS, MX).
  3. Fingerprint Matching: Compare resolved targets against provider-specific signatures indicating a deleted or unclaimed resource.

Remediation Steps

For each finding, the scanner provides provider-specific remediation instructions:

Delete the Dangling Record

The safest fix is to remove the DNS record entirely if the service is no longer needed.

# Auto-delete via integrated DNS provider
subtakeover remediate delete example.com old-app.example.com

# Manual deletion (Cloudflare example)
curl -X DELETE "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/dns_records/$RECORD_ID" \
  -H "Authorization: Bearer $CF_API_TOKEN"

Reclaim the Resource

If the subdomain should remain active, re-register the cloud resource with the exact name shown in the finding.

# Re-create an S3 bucket matching the dangling CNAME
aws s3 mb s3://old-app-assets --region us-east-1

# Re-deploy a Heroku app with the original name
heroku apps:create old-app-name
Reclaiming only works if the provider allows re-registration of deleted resource names. Some providers (e.g., Heroku) permanently block reuse after deletion.

Verify Remediation

# Re-scan a single subdomain after fix
subtakeover scan example.com --target old-app.example.com

# Verify via API
curl http://localhost:8401/api/v1/findings/old-app.example.com/verify

Troubleshooting

Common Issues

No subdomains enumerated: Ensure CT log access isn't blocked by your network. Try --enum-method dns-brute to fall back to wordlist-based discovery.

False positive on active service: The cloud service may return a generic error that matches a dangling signature. Suppress with subtakeover finding suppress old-app.example.com --reason "Active service".

DNS provider auth fails: Verify token permissions include read/write for DNS zones. Test with subtakeover provider test <provider>. Check ~/.edgeiq/logs/subtakeover.log for detailed errors.

Scan hangs on resolution: Increase resolver timeout with --dns-timeout 10. Some authoritative nameservers rate-limit queries; use --resolvers 1.1.1.1,8.8.8.8 to distribute load.

Missed takeover on known-vulnerable subdomain: Run subtakeover fingerprint update to refresh signatures. If the provider isn't covered, submit a pattern via subtakeover fingerprint submit.

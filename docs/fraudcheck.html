FraudCheck Documentation

Overview

FraudCheck is a lightweight, $9/month fraud detection service designed specifically for checkout pages, payment flows, and brand-sensitive transactional surfaces. It combines real-time behavioral analysis, brand impersonation heuristics, and payment URL validation to flag suspicious activity before revenue loss occurs.

Unlike general-purpose fraud platforms that require extensive integration and tuning, FraudCheck ships with sensible defaults for e-commerce and SaaS checkout environments. It monitors DOM integrity, validates payment processor URLs against known-good patterns, detects credential harvesting overlays, and alerts on brand impersonation attempts in real time.

Setup

To enable FraudCheck:

  1. Navigate to Dashboard → FraudCheck → Enable.
  2. Add your protected domains under Protected Origins. Only HTTPS origins are accepted.
  3. Install the snippet: copy the generated <script> tag from Dashboard → FraudCheck → Install Snippet and paste it immediately before </body> on every checkout or payment page.
  4. (Optional) Configure webhook endpoints at Integrations → Webhooks for real-time alert delivery.
  5. Verify installation using the built-in test harness at FraudCheck → Verify Installation. The harness simulates three common attack vectors and confirms detection.

The snippet is under 4 KB gzipped and adds no perceptible latency. It loads asynchronously and fails open — if the script cannot reach EdgeIQ servers, the checkout proceeds normally without blocking.

Detection Indicators

FraudCheck evaluates signals across four categories:

  • DOM Integrity: Detects injected iframes, shadow DOM overlays, form action rewriting, and unexpected mutation observer activity on payment fields.
  • Brand Impersonation: Flags visual mimicry of known payment processors (Stripe, PayPal, Square), including logo similarity, color palette matching, and font fingerprinting against a maintained brand registry.
  • Behavioral Anomalies: Identifies non-human input patterns, clipboard hijacking attempts, autofill abuse, and rapid field-focus cycling consistent with bot-driven checkout.
  • Network Context: Correlates client IP reputation, TLS fingerprint consistency, and geographic velocity checks against historical session baselines.

Each indicator produces a confidence score (0–100). Alerts fire when the composite risk score exceeds the configured threshold (default: 75).

URL Verification API

The URL Verification API allows server-side validation of payment redirect URLs before they are presented to users. This prevents open-redirect exploitation and ensures post-checkout destinations match declared merchant intent.

# Verify a payment URL
POST /api/v1/fraudcheck/verify-url
Authorization: Bearer «redac...e_…»
Content-Type: application/json

{
  "url": "https://checkout.stripe.com/pay/cs_test_...",
  "expected_merchant": "acme_corp",
  "context": "post_checkout_redirect"
}

# Response
{
  "valid": true,
  "processor": "stripe",
  "merchant_match": true,
  "risk_score": 12,
  "warnings": []
}

Supported processors: Stripe, PayPal, Square, Adyen, Braintree, Shopify Payments, and Paddle. Custom processor patterns can be registered via Dashboard → FraudCheck → Custom Processors.

Rate limit: 300 requests/minute per API key. Responses are cached for 60 seconds per unique URL hash to prevent redundant lookups during retry storms.

Integration Guide

Client-Side Snippet

The snippet automatically instruments all <form> elements containing inputs with name, id, or autocomplete attributes matching common payment field patterns (cc-number, cardnumber, exp-month, etc.). No manual tagging is required.

To exclude specific forms from monitoring, add data-fraudcheck-ignore to the form element.

Server-Side Webhook Payload

{
  "event": "fraudcheck.alert",
  "timestamp": "2026-11-06T14:22:18Z",
  "origin": "https://shop.example.com",
  "risk_score": 88,
  "indicators": [
    {"type": "dom_integrity", "detail": "iframe_injection", "confidence": 92},
    {"type": "brand_impersonation", "detail": "paypal_logo_mismatch", "confidence": 84}
  ],
  "session_id": "fc_sess_8f3a...",
  "client_ip_hash": "sha256:a1b2c3..."
}

All payloads are signed with HMAC-SHA256 using your webhook secret. Validate signatures before processing. See Dashboard → Integrations → Webhooks → Signing Keys.

Alert Configuration

Configure alert routing and thresholds at Dashboard → FraudCheck → Alerts:

  • Risk Threshold: Adjust the composite score trigger point (0–100). Lower values increase sensitivity but may raise false positives on legitimate edge cases (e.g., corporate proxies, accessibility tools).
  • Channels: Email, Slack, Discord, PagerDuty, or custom webhook. Multiple channels can be active simultaneously.
  • Suppression Rules: Suppress alerts for known-safe IPs, user agents, or geographic regions. Suppressions are logged for audit.
  • Digest Mode: Batch low-severity alerts into hourly digests instead of firing individually. High-severity alerts (score ≥ 90) always fire immediately regardless of digest settings.

Alert metadata includes full indicator breakdown, session replay link (if enabled), and one-click false-positive reporting.

Troubleshooting

  • Snippet not detecting forms: Confirm the script loads after the DOM is ready. If using SPA frameworks, call window.FraudCheck.rescan() after route transitions. Verify no CSP policies block inline script execution.
  • False positives on legitimate checkouts: Review the indicator breakdown in the alert. Common benign triggers include browser extensions modifying payment fields and corporate security overlays. Add suppression rules or adjust threshold accordingly.
  • Webhook deliveries failing: Ensure your endpoint returns 2xx within 10 seconds. Use Integrations → Webhooks → Test Delivery to validate connectivity and signature verification. Failed deliveries retry up to 5 times with exponential backoff.
  • URL Verification API returning valid: false for known-good URLs: Check that the expected_merchant parameter matches the registered merchant slug exactly (case-sensitive). Newly added processors may take up to 1 hour to propagate to all edge nodes.
  • High latency on checkout pages: The snippet is async and should not block rendering. If performance degradation is observed, verify no synchronous scripts are chained after the FraudCheck snippet and confirm CDN cache hit ratios for the script asset.

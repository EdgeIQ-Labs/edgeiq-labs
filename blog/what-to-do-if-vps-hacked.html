What to Do If Your VPS Is Hacked: Incident Response for SMBs

Incident Response VPS Cornerstone

You found the signs. Weird processes, unknown SSH keys, outbound traffic to suspicious IPs, or maybe a ransom note. Your VPS is compromised. Here's exactly what to do in the next hour, day, and week.

This playbook assumes you're a small business without a dedicated IR team. It prioritizes containment over forensics because stopping active damage matters more than preserving perfect evidence when you're a team of five. For the full first-24-hours checklist applicable beyond VPS incidents, see our incident response checklist.

Hour 0: Confirm and Contain

Before panicking, confirm the compromise is real. False positives waste time and cause unnecessary downtime.

Verify the Indicators

  • Check running processes: ps aux | grep -E 'crypto|miner|xmrig|ncat|nc '
  • Check recent logins: last -20 and cat /var/log/auth.log | grep -i failed
  • Check open ports: ss -tlnp — anything unexpected?
  • Check crontabs: crontab -l and ls -la /etc/cron.*
  • Check authorized_keys: cat ~/.ssh/authorized_keys — recognize every key?

If confirmed, contain immediately. Don't investigate yet. Stop the bleeding first.

Containment Steps

  • Snapshot the server — preserve current state for later forensics before making changes
  • Block outbound traffic — iptables -P OUTPUT DROP except your IP and essential services
  • Kill suspicious processes — kill -9 PID for confirmed malicious processes
  • Disable compromised accounts — passwd -l username for any suspect users
  • Rotate credentials — assume all passwords and keys on this server are burned

If customer data may be involved, trigger your breach notification process now. Waiting makes it worse legally and reputationally. Our ransomware readiness checklist covers notification timelines.

Day 1: Investigate the Entry Point

With containment in place, figure out how they got in. Without this, rebuilding just gives them the same door back in.

Common VPS Compromise Vectors

  • Weak SSH credentials — password auth enabled, root login allowed, no fail2ban. Check /var/log/auth.log for brute force patterns.
  • Unpatched services — outdated nginx, Apache, WordPress, Node.js with known CVEs. Cross-reference installed versions against our vulnerability exploitation timeline analysis.
  • Exposed admin panels — phpMyAdmin, wp-admin, cPanel on default ports with weak passwords. Our exposed admin panel guide shows how attackers discover these.
  • Compromised dependencies — supply chain attacks via npm, pip, or Docker images. Run our repo scanner to check for leaked credentials that may have enabled lateral movement.
  • Misconfigured cloud storage — S3 buckets, database ports open to 0.0.0.0/0. See our cloud misconfiguration checklist.

Log Analysis Priority

  1. /var/log/auth.log — successful logins from unknown IPs
  2. /var/log/syslog — service restarts, kernel messages, cron executions
  3. Application logs — web access logs showing exploit attempts or data exfiltration
  4. Bash history — cat ~/.bash_history for commands the attacker ran

If you have Wazuh or another SIEM deployed, query it for alerts during the suspected timeframe. Our monitoring routine guide covers setting up SIEM for small teams. If you don't have monitoring, this incident is your motivation to deploy it.

Day 2-3: Remediate and Rebuild

Don't try to clean a compromised server. Rebuild from known-good state.

Why not clean? Rootkits persist across reboots. Backdoors hide in kernel modules, firmware, or legitimate-looking system files. You'll spend days hunting and still miss something. Rebuilding takes hours and gives you certainty.

Rebuild Process

  1. Provision fresh VPS — new instance, patched OS, hardened baseline
  2. Restore from verified backup — only application data and configs, NOT binaries or system files. Verify backup integrity before restoring.
  3. Apply all patches — OS, application, dependencies. Check our recent CVE coverage for critical patches.
  4. Harden SSH — disable password auth, disable root login, use key-only, install fail2ban
  5. Configure firewall — allow only necessary ports. Run our port scanning guide to verify.
  6. Deploy monitoring — Wazuh agent, file integrity monitoring, log collection. This is non-negotiable post-incident.
  7. Test thoroughly — verify every endpoint, form, API, and integration works before switching traffic
  8. Switch DNS — update A records with low TTL, monitor for issues
  9. Decommission old server — only after 48 hours of clean operation on new instance

Week 1: Post-Incident Review

After recovery, conduct a blameless post-mortem. The goal isn't punishment, it's preventing recurrence.

Post-Incident Questions

  • How did they get in? (Root cause)
  • How long were they present before detection? (Dwell time)
  • What data was accessed or exfiltrated? (Impact scope)
  • What monitoring would have caught this earlier? (Detection gap)
  • What hardening would have prevented entry? (Prevention gap)
  • What needs to change in our processes? (Process improvement)

Document findings. Update your security policy framework based on lessons learned. Schedule follow-up reviews at 30 and 90 days to verify improvements stuck.

Preventing the Next Incident

Every compromise is a learning opportunity. Here's what to implement based on common root causes:

  • If SSH brute force: Disable password auth, deploy fail2ban, use key-only authentication
  • If unpatched CVE: Implement automated patching or switch to managed VPS with weekly patch cycles
  • If exposed admin panel: Move to VPN-only access or IP whitelist. Run our subdomain scanner regularly to find forgotten panels.
  • If no monitoring detected it: Deploy Wazuh SIEM. Our Compliance Shield includes managed monitoring from $299/mo.
  • If backups failed: Implement automated backup verification. Test restores quarterly.
  • If credentials were reused: Deploy password manager, enforce unique credentials per service

Email Header Analyzer Documentation

Price: Free · No account required

Overview

The Email Header Analyzer is a free tool that parses raw email headers to evaluate sender authentication, trace delivery paths, and detect signs of spoofing. It extracts and interprets SPF, DKIM, and DMARC results from Authentication-Results headers, reconstructs the Received chain to visualize hop-by-hop delivery, and flags common indicators of forged or manipulated messages.

All processing occurs client-side in your browser. Raw headers are never transmitted to EdgeIQ Labs servers.

How to Use

  1. Navigate to the Email Header Analyzer page.
  2. Copy the full raw headers from an email message (see Pasting Raw Headers below for client-specific instructions).
  3. Paste the headers into the input text area.
  4. Click Analyze.
  5. Review the structured output across the Authentication, Received Chain, and Spoofing Indicators tabs.

The tool accepts headers in standard RFC 5322 format. Body content is ignored if included, but pasting only headers reduces noise and speeds parsing.

Interpreting Results

The analyzer evaluates three core authentication protocols. Each produces a result status that indicates whether the sending server was authorized to send on behalf of the claimed domain.

SPF (Sender Policy Framework)

SPF verifies that the connecting IP address is listed in the domain's DNS SPF record.

  • pass — The sending IP is authorized by the envelope sender domain's SPF record.
  • fail — The sending IP is explicitly not authorized. Strong indicator of spoofing.
  • softfail — The sending IP is not authorized, but the domain owner uses ~all instead of -all. Treat as suspicious.
  • neutral — The domain's SPF record makes no assertion about this IP.
  • none — No SPF record was published for the domain.
  • temperror / permerror — A DNS lookup failure or syntax error prevented evaluation.

DKIM (DomainKeys Identified Mail)

DKIM validates a cryptographic signature embedded in the message headers against a public key published in DNS.

  • pass — The signature is valid and the signed headers were not modified in transit.
  • fail — The signature exists but does not validate. Indicates tampering or forgery.
  • policy — The signature passed cryptographically but violated a domain policy constraint.
  • neutral — A DKIM signature is present but could not be evaluated definitively.
  • none — No DKIM signature was found in the headers.
  • temperror / permerror — DNS retrieval of the public key failed or the signature syntax was invalid.

DMARC (Domain-based Message Authentication, Reporting & Conformance)

DMARC requires that either SPF or DKIM passes and that the authenticated domain aligns with the From header domain.

  • pass — At least one of SPF or DKIM passed with identifier alignment to the From domain.
  • fail — Neither SPF nor DKIM passed with alignment. The receiving server should apply the domain's published DMARC policy (p=none, p=quarantine, or p=reject).
  • none — No DMARC record was published for the From domain.

Alignment note: SPF aligns the Return-Path (envelope-from) domain with the From header domain. DKIM aligns the d= signing domain with the From header domain. Alignment can be strict (exact match) or relaxed (organizational domain match). The analyzer reports which alignment mode applies.

Received Chain Analysis

The Received headers form a chronological chain documenting each mail transfer agent (MTA) that handled the message. The analyzer reverses and structures this chain so you can read it top-down from origin to destination.

For each hop, the tool extracts and displays:

  • Timestamp: When the MTA accepted the message. Gaps between hops may indicate queuing delays or deliberate stalling.
  • Source IP & Hostname: The connecting IP and its reverse-DNS name. The analyzer performs a forward-confirmed reverse DNS (FCrDNS) check where possible.
  • Receiving Server: The MTA that logged the hop (e.g., mx.example.com).
  • Protocol: ESMTP, SMTPS, or internal routing markers.

Warnings are raised when:

  • A hop's source IP has no PTR record or the PTR does not resolve back to the same IP (FCrDNS mismatch).
  • Timestamps move backward, indicating clock skew or header manipulation.
  • The first (originating) hop IP does not match the IP validated by SPF.
  • Unexpected geographic routing appears (e.g., a domestic message routed through foreign infrastructure).

Common Spoofing Indicators

The analyzer flags patterns commonly associated with forged or malicious emails. These indicators supplement, but do not replace, the authentication results above.

  • From / Return-Path mismatch: The visible From address differs from the envelope sender in Return-Path. Legitimate mailing lists may cause this, but unexpected mismatches warrant scrutiny.
  • Display name spoofing: The display name contains an email address that differs from the actual From address (e.g., "ceo@company.com" <attacker@evil.com>).
  • Missing Authentication-Results: The receiving MTA did not stamp authentication results, making verification impossible from headers alone.
  • SPF fail + DKIM none: No authentication mechanism validated the sender. High confidence spoofing signal.
  • DMARC fail with p=reject: The domain owner requested rejection of unauthenticated mail, yet the message was delivered. This suggests the receiving server is non-compliant or the headers were injected post-delivery.
  • Suspicious X-Mailer / User-Agent: Bulk-mail tools, scripting libraries, or mismatched client identifiers relative to the claimed sender organization.
  • Inconsistent Message-ID domain: The Message-ID domain does not match the sending infrastructure or the From domain.
  • Received chain anomalies: Missing hops, duplicate timestamps, or originating IPs from known malicious ranges.

Each indicator is tagged with a severity level: High (strong spoofing evidence), Medium (suspicious but potentially legitimate), or Low (informational).

Export Options

After analysis, you can export the results for reporting, sharing, or archival purposes:

  • JSON: Structured machine-readable export containing all parsed headers, authentication results, received chain data, and flagged indicators. Suitable for integration with SIEM tools or custom pipelines.
  • CSV: Tabular format with one row per received hop and summary rows for SPF/DKIM/DMARC status. Opens directly in spreadsheet applications.
  • PDF Report: Formatted document with executive summary, detailed findings tables, and the reconstructed received chain. Designed for attaching to incident tickets or compliance records.
  • Plain Text: Annotated text dump of the parsed and interpreted headers. Useful for pasting into ticketing systems or chat channels.

Export buttons appear at the bottom of the results panel after a successful analysis. All exports are generated client-side.

Troubleshooting

"No headers detected" error

The parser could not identify any valid RFC 5322 headers in the input. Common causes:

  • You pasted the email body instead of the headers. Refer to Pasting Raw Headers for your email client.
  • Headers were copied from a rich-text editor that stripped line breaks. Paste into a plain-text editor first, then re-copy.
  • The input contains only partial headers missing the leading field names.

SPF shows "none" but I know the domain has an SPF record

The analyzer reads the Authentication-Results header stamped by the receiving MTA. If the receiving server did not perform SPF evaluation or did not record it, the analyzer cannot infer the result. Check whether the receiving MTA is configured to stamp authentication results per RFC 8601.

DKIM shows "fail" for forwarded emails

Forwarding often breaks DKIM signatures because intermediate MTAs modify headers (e.g., adding Subject: [Fwd:] prefixes or appending list footers). This is expected behavior. In forwarding scenarios, rely on SPF alignment or ARC (Authenticated Received Chain) seals if available.

Received chain appears incomplete

Some MTAs strip earlier Received headers for privacy or anti-spam reasons. Internal relay hops within the same organization may also be consolidated. The analyzer works with whatever headers are present; missing hops will be noted as gaps in the timeline.

Tool hangs or crashes on paste

Extremely large inputs (e.g., pasting the entire raw message including a multi-megabyte base64 attachment body) can exhaust browser memory. Paste only the header block — everything above the first blank line. If the issue persists, clear the page cache and try again in a private/incognito window.

DMARC alignment shows "fail" despite SPF pass

SPF authenticates the Return-Path domain, not the From domain. If these differ (common with mailing lists, transactional email services, and SaaS platforms using custom return paths), SPF passes but DMARC alignment fails unless DKIM provides an aligned pass. Check whether the sending service supports DKIM signing with your From domain.
